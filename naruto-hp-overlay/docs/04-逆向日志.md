# 逆向日志

记录「找技能冷却」这一路试过并排除掉的所有方法，避免后来人重复劳动。

**目标**：定位场内 2 技能的冷却剩余时间。已知约束：CD = 10 秒，按钮上显示整数秒并倒数。

**结果：没找到。** 12 种方法，覆盖约 2.4 GB 可读堆，0 命中 —— 而屏幕上确实显示着 `7`。

---

## 排除路径

### 1. 血量块附近 ±128 KB
只有粒子和渲染矩阵（`-2.621` 之类的值），仅 5 个页有变化。
`tools/cd_page.py`、`tools/cd_rec.py`

### 2. 属性记录 `0x240` 本身
14 秒内只有 `+0x078` 一个字段有微值变化，无倒计时。

### 3. 血块所在堆区 +64 MB（3 Hz × 24 s）
只找到 9 个 **`0 ↔ 10` 方波**（值为 10.00 常驻，某一时刻整片归零）—— 那是回合结束清标志，同一时刻一起变，不是倒计时。
`tools/cd_saw.py`

### 4. GC 堆 `72E5C0000000 ~ 72E5D0000000` 全 256 MB
4 段 × 64 MB，各 22 秒，无 0~10 锯齿。
`tools/cd_any.py`

### 5. HUD 根对象 ±8 MB
我方/敌方血块共用 `owner = 72E4EB03B360`，技能按钮应在它的子节点上。16 MB @ 3 Hz × 30 s，无命中。
补测：修正「量程必须 ≥3」的过滤器 bug 后重扫，仍无。
`tools/cd_scan.py`

### 6. 周期对齐法（最狠的一招，也失败了）
CD 周期恰好 10 秒 → 隔 5 秒读两次，同一字段必然差 `5.0`（若是 fillAmount 则差 `0.5`）。一次采样即可覆盖全堆。

| 间隔 | 命中数 |
|---|---|
| 5.0 s | 26 125 |
| 2.0 s | 54 206 |
| **交集** | **479** |

479 个交集逐个人工验证，全是 `0 ↔ 0.5` 的 UI 动画和垃圾区。
`tools/cd_period.py`

### 7. 毫秒型倒计时（0 ~ 10000）
很多引擎把 CD 存毫秒。只有 14 个到 1704 的动画值。
`tools/cd_wide.py`

### 8. `fillAmount`（0 ~ 1 环形遮罩）
Unity 技能遮罩最常用的存法。这里犯过一个关键 bug：漏斗筛选写死「量程 ≥ 3」，把 0~1 的值全部误杀，修好后重扫 HUD 区仍无。

### 9. 指针回溯
`huoying.exe --ptrscan <地址> [范围]`：全堆找指向目标地址的 qword，2.4 GB 约 20 秒。
指向血量块的持有者集中在 `72E53B606xxx`，**20 秒后整片归零** —— 每帧重建的渲染快照列表，不是持久对象。

### 10. 对象树两跳展开
从属性记录里的 19 根指针出发，展开 60 个对象、采样 20 秒，**只有 3 个字段在动**（其中一个是全局时间副本），CD 不在这棵树里。
`tools/cd_tree.py`

### 11. 全堆 UI widget 枚举
`huoying.exe --widgets`：按血块那个结构（进度条描述符）扫全堆，只找到 **3 个** widget（双方血条 + 1 个未知名），全部恒为 1.0 —— 技能冷却遮罩不是这个 widget 类。

### 12. 剩余未覆盖区域
`72E5F0000000`（压缩数据区，19 万噪声）、`72E580` / `72E648` / `72E670` / `72E6DC`：全部 0 命中。

## 误判过的假信号

| 地址 | 真相 |
|---|---|
| `72E5C115xxx` | 回收垃圾区 |
| `72E4C0E008EC` | 4×4 变换矩阵，stride `0x50` |
| `72E4C017BD2C` | 值 `5.000 → 0.000` 看着极像，实际是 `-312149` 垃圾 |
| `72E5C7E5BF34` | 图形缓冲区垃圾 |
| `72E4C7CA45F8` | 用户手动搜到的「浮点型」，是图形缓冲，不是 CD |

## 检测器自身踩过的 bug

| bug | 后果 |
|---|---|
| 写死「量程必须 ≥ 3」 | 误杀全部 0~1 的 fillAmount |
| 用 `gzip.decompress` 解大流 | CRC 错，整批候选被丢弃（改 `zlib.decompressobj(16+MAX_WBITS)`） |
| 三拍采样周期 33 秒 | CD 只有 10 秒，采到的两帧之间早已走完 |
| `cd_pipeline` 串行 535 次 adb 调用 | 50 秒只采到 3 帧（改 10~16 线程） |
| 200 线程并发 adb | 直接卡死 60 秒超时 |

---

## 结论与建议

CD **大概率不是「递减数值」**。两个更可能的方向：

1. `结束时间戳 + 全局时间` 现场计算 —— 内存里只有全局时间（已找到 4 个）和一个 +10 的时间戳，没有 0~10 的中间值；
2. 被拆进压缩结构或位域里。

真要挖，正路是 **il2cpp 类表枚举**：`tools/ic.py` 已经能用（拿到 `System.String` 的 klass 之后，顺着 `image → types` 枚举全部类），缺的只是把类表全量拉出来按名字筛 `Skill` / `CD` / `Cool`。

## 读内存性能基线

| 操作 | 耗时 |
|---|---|
| 裸读 1 MB / 4 MB / 16 MB | 52 / 119 / 277 ms（≈ 58 MB/s 单通道） |
| C++ 6 线程 gzip 聚合 | ≈ 132 MB/s |
| 28 KB 页区高频采样 | 29 Hz |
| 全堆 2.6 GB 扫描 | ≈ 19 s |
